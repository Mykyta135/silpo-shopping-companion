# План перебудови під «Супутник у залі»

## Що зберігається без змін

Уся інфраструктура MCP уже написана й перевірена на живому сервері —
її чіпати не треба.

| Файл | Чому лишається |
| --- | --- |
| `mcp/silpo-mcp.service.ts` | OAuth 2.1 + PKCE, сесії, `tools/list` — працює |
| `mcp/silpo-auth.provider.ts` | Провайдер авторизації |
| `mcp/token-store.ts` | Серверне зберігання токенів — **вимога хакатону** |
| `mcp/auth.controller.ts` | Флоу логіну |
| `agent/mcp-tools.factory.ts` | Міст MCP → AI SDK, `dynamicTool` |
| `quest/receipts.ts` | **Парсинг чеків + фільтр за датою — ядро аналітики** |
| `agent/agent.*` | Вільний чат — лишається як запасний сценарій демо |

`receipts.ts` особливо цінний: розбір вкладених форматів чеків уже написаний
і покритий тестами. Перейменується в `shopping/receipts.ts`.

## Що видаляється

Квестова логіка: `quest/journey.store.ts`, `quest/quest-prompts.ts`,
`quest/quest.service.ts`, `quest/quest.controller.ts`, `quest/quest.schemas.ts`,
`packages/shared/src/quest.ts`, екрани `JourneyMapScreen`, `LevelScreen`.

Зберігається як довідка: `docs/product-logic.md`.

## Нова структура API

```
apps/api/src/shopping/
├── receipts.ts            (перенесено з quest/, без змін)
├── price-history.ts       ціна в чеку vs catalogProduct.price
├── rhythm.ts              ритм покупок → що закінчується
├── coupons.ts             звірка купонів з раціоном (N+1 виклик деталей)
├── zones.ts               категорія → зона → порядок обходу
├── list.service.ts        фаза 1: складання списку (агентний ланцюжок)
├── companion.service.ts   фаза 2: реакція на події в залі
├── list.store.ts          стан списку (за зразком journey.store.ts)
├── shopping.controller.ts REST
└── shopping.module.ts
```

### Ключові модулі

**`zones.ts`** — серце маршруту. Мапить категорію товару на зону, зони мають
фіксований порядок обходу (галузевий стандарт, див.
[concept-store-companion.md](concept-store-companion.md)). Чиста функція,
легко тестується, не потребує MCP.

**`price-history.ts`** — рахує подорожчання з даних, які вже є в чеку.
Не потребує додаткових викликів.

**`rhythm.ts`** — з дат чеків виводить періодичність позиції.
На 4 чеках працює грубо; чесно позначати впевненість.

**`coupons.ts`** — `get_my_coupons` + `get_coupon_details` для кожного,
далі **модель** звіряє текстовий опис купона з раціоном (списку товарів
API не дає).

## Ендпоїнти

| Метод | Шлях | Призначення |
| --- | --- | --- |
| `POST` | `/shopping/list` | Фаза 1: агент складає список (проактивно) |
| `PATCH` | `/shopping/list` | Гість править: додає / прибирає позицію |
| `POST` | `/shopping/event` | Фаза 2: подія в залі → реакція агента |
| `GET` | `/shopping/list` | Поточний стан |
| `POST` | `/shopping/cart` | Перенести список у реальний кошик + checkout |

`POST /shopping/event` — головний для критерію агентності. Приймає
`{ type: 'picked' \| 'missing' \| 'zone-left', productId? }`, повертає
репліку агента (або мовчання) + виклики tools.

## Ризики

- **`get_coupon_details` — N+1 виклик.** На 9 купонах прийнятно, закласти кеш.
- **Реакції фази 2 не можна тестувати без магазину.** Потрібен режим симуляції
  подій для демо.

## Результати перших модулів (виміряно на реальних чеках)

### `zones.ts` ✅ сильний
Усі 48 товарів з реальних чеків розкладені правильно. Тести спіймали
три хибні збіги, які інакше пройшли б непоміченими: «Куркума» → м'ясо
(через стем «курк»), «Тунець салатний» → овочі (через «салат»),
«Лосось стейк» → м'ясо (правило риби мусить іти перед м'ясом).

### `price-history.ts` ✅ сильний, але з продуктовим висновком
Порівняно 36 позицій, пропущено 13 (немає ціни в каталозі).

**Індекс кошика вийшов +2.8%** — і це проблема подачі, а не коду.
Зважування за витратами розмиває біль: дорогі позиції (тунець, філе)
не змінились і тягнуть середнє вниз, тоді як окремі позиції зросли
на 45%, 43%, 32%.

> **Висновок для UI:** показувати треба **конкретні позиції**, а не агрегат.
> «Гриби +45%» вражає, «кошик +2.8%» — ні.

### `rhythm.ts` ✅ працює — перевірено на синтетичній історії

Проблема була в **даних, а не в коді**. Щоб це довести, згенеровано
[synthetic-history.json](../apps/api/src/shopping/__fixtures__/generate-history.mjs):
**75 чеків за рік, 344 позиції, 13 товарів із заздалегідь відомими циклами**.

Результат: **середня похибка 4%, максимум 10%**.

| Товар | Реальний цикл | Виявлено |
| --- | --- | --- |
| Сир President | 21 дн | 21.1 |
| Яйця | 14 дн | 13.5 |
| Молоко | 7 дн | 7.3 |
| Кава | 30 дн | 32.0 |

Три аномалії теж оброблені правильно: разові покупки → `none`,
top-up (двічі за 3 дні) → `low`, покинутий товар (127 днів при циклі 12) →
відсіяний зі списку.

**На реальному акаунті (4 чеки) ритм мовчить** — і це правильна поведінка,
а не поломка. Демо все одно варто будувати навколо цін і купонів.

### Адаптивні пороги замість захардкоджених

Три константи були припущеннями про «середню людину». Замінені на
величини, що масштабуються від самих даних:

| Було | Стало |
| --- | --- |
| Шум = гап < 5 днів | Гап < 40% від **медіанного циклу товару** |
| Покинуте = 3 цикли | 2.5 / 3.5 / 5 циклів **залежно від впевненості** |
| Поріг ціни = 15% | **1.5× медіанного зростання в кошику гостя** (8–30%) |

Головна помилка, яку це виправило: 5 днів — це top-up для кави (цикл 30)
і повний цикл для хліба (цикл 5). Порівнювати їх однією міркою не можна.

Медіана як основа — бо вона стійка до викидів: пара коротких top-up'ів
не зсуває її так, як зсунула б середню.

Поріг ціни на синтетиці піднявся до 30% (ціни гуляють сильно) і залишив
3 справді помітні стрибки замість шуму; на реальних даних лишився 15% —
замало точок, спрацював запобіжник.
