# Модель взаємодії: гібридний список + реактивний агент

Рішення прийнято 2026-08-09. Доповнює
[concept-store-companion.md](concept-store-companion.md).

## Дві фази

### Фаза 1 — до магазину: гібридне складання списку

Ні «агент вирішив усе», ні «гість надиктував». **Обидва вкладаються, гість
завжди має останнє слово.**

```
Агент пропонує (проактивно)          Гість править
├─ закінчується за ритмом чеків  →   ✓ лишає / ✗ прибирає
├─ купон згорає через 2 дні      →   ✓ лишає / ✗ прибирає
├─ подорожчало → є заміна        →   ✓ бере заміну / ✗ лишає своє
└─ «спробуй нове» під раціон     →   ✓ лишає / ✗ прибирає
                                      + додає своє текстом/голосом
```

Кожна пропозиція агента **несе причину**: не «купи молоко», а «молоко —
береш кожні 10 днів, минулого разу 23.05». Причина — те, що відрізняє
рекомендацію від реклами.

### Фаза 2 — у залі: реактивний агент

Гість викреслює позиції на ходу. **Кожне викреслення — подія, на яку агент
може відреагувати.**

Реакція не завжди потрібна — агент мовчить за замовчуванням і озивається,
лише коли має що сказати:

| Подія | Реакція агента |
| --- | --- |
| Взяв товар, до якого є невикористаний купон | «До цього сиру є купон за 1 грн — візьми ще один» |
| Взяв позицію, що подорожчала | «Це +30% з травня. Поруч є заміна за 28.49» |
| Пропустив зону й пішов далі | «Ти минув молочку, там лишились 2 позиції» |
| Зібрав усе зі списку | «Все зібрано. Каси прямо» |
| Товару немає на полиці (гість каже) | `get_replacements` → альтернатива в цій же зоні |

## Два неочевидні рішення

### 1. Агент має право не мовчати, але не має права набридати

Ліміт: **не більше однієї репліки на зону**. Інакше продукт перетворюється
на ті самі попапи, від яких ми тікаємо.

Пріоритет реплік, якщо приводів кілька: купон, що згорає > заміна дорогої
позиції > пропущена зона > «спробуй нове».

### 2. Відсутність товару вводить гість, не система

`catalogProduct.available` **не можна використовувати** як сигнал наявності
на полиці — на тестових даних `stock: 0` стояв на всіх 42 позиціях через
застарілий таймслот (див. [mcp-data-findings.md](mcp-data-findings.md)).

Тому: кнопка «немає на полиці» у гостя → агент викликає `get_replacements`.
Це чесніше й заодно **дає бізнесу дані про реальні порожні полиці** —
те, чого немає в жодній системі.

## Чому саме це закриває критерій «агентність»

Бриф вимагає «здатність працювати з контекстом, використовувати інструменти,
виконувати послідовність дій».

- **Контекст** — агент пам'ятає, що вже викреслено, в якій зоні гість, які
  купони не використані
- **Інструменти** — 10+ tools у фазі 1, `get_replacements` / `find_products_batch`
  реактивно у фазі 2
- **Послідовність** — фаза 1 будує план, фаза 2 його виконує з відхиленнями
- **Рішення** — агент сам вирішує, коли озватись, а коли змовчати

Це не «чат, що відповідає на питання». Це агент, що **веде процес**.

## Що показувати на демо

Ліва частина екрана — список за зонами. Права (або низ) — **лог викликів
tools у реальному часі**. Бриф прямо заохочує: «запис екрана, лог JSON-RPC
або трейси».

Ключовий момент демо: гість викреслює сир → на екрані видно
`get_my_coupons` → `get_coupon_details` → агент каже про купон за 1 грн.
**Видно причину й видно інструмент.**

## Відкриті питання

- **Офлайн.** У залі може не бути звʼязку. Список має працювати без мережі,
  реакції — деградувати м'яко.
- **Затримка чеків** не виміряна — впливає на те, чи можна реагувати на
  «щойно куплене» одразу після каси.
- **Введення в залі.** Тап по чекбоксу — обов'язково. Голос — опційно,
  якщо лишиться час.
